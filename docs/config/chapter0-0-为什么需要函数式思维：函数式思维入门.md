# 为什么需要函数式思维：函数式思维入门

你好，在深入本配置库之前，有一个问题需要我们想清楚：什么是函数式思维？

你可能早已熟悉 Stream、Function API，用它们处理起业务来得心应手。但很多开发者只停留在“会用”的阶段，而它们背后，其实藏着一套与传统 Java 迥异的编程理念——这就是我们常说的函数式思维。

本文不会讲复杂的函数式理论，我们只回答一个问题：

> 为什么 Stream、Lambda 这些看似比较神奇的东西，会让代码变得更简洁、更容易维护？

为了回答这个问题，我们只需要理解三个概念：

* 做什么，而不是怎么做
* 不可变性
* 纯函数

## 做什么，而不是怎么做

我们在写 Java 的时候，肯定避免不了一些 for 循环和 if-else 判断。

比如，我们要在列表中筛选出所有有效的用户，用传统的命令式写法，肯定是要分以下几步的：

* 创建一个新的空列表
* 遍历用户列表
* 判断用户是否有效
* 将结果放入新列表

那么我们会得到这样的代码：

```java
List<User> validUsers = new ArrayList<>();

for (User user : users) {
    if (user.isValid()) {
        validUsers.add(user);
    }
}
```

如果要提取所有用户名称：

```java
List<String> names = new ArrayList<>();

for (User user : users) {
    names.add(user.getName());
}
```

可以看到，代码中无一不透露着一种 "你应该这样做，然后再这样做，最后这样做"的氛围。这种思维方式我们称它为命令式编程（Imperative Programming）。

它关注的是如何一步一步完成任务。

但如果换成 Stream：

```java
List<User> validUsers = users.stream()
        .filter(User::isValid)
        .toList();

List<String> names = users.stream()
        .map(User::getName)
        .toList();
```

是不是突然就不一样了？

我们不再关心循环怎么写、集合怎么创建、元素怎么加入。

我们只关心"我要什么结果", 这就是函数式思维最核心的思想：**描述结果，而不是描述过程。**

或者换一种说法：

> 做什么，而不是怎么做。

## 不可变性

仅仅描述结果，就能让代码变得更可靠吗？

还远远不够呢。

因为还有一个更麻烦的问题：状态。

大部分 Bug 的本质，其实都和状态变化有关。

例如：

```java
user.setName("小雪");

user.setAge(18);

user.setValid(false);
```

对象会变。 变量会变。 什么都会变。

程序运行过程中，状态不断发生变化。

于是我们经常会遇到这样的情况：

```text
刚创建的时候是正确的

传了几个方法之后变了

最后发现不知道是谁改的
```

为了减少这种问题，函数式编程提倡一种思想：

> 如果一个对象创建出来之后根本不能修改，哪还有这么多问题啊。

事实上，Java 这些年也一直在朝这个方向发展。

Record 就是其中最典型的代表。

借助记录类，我们可以使用一行代码定义一个不可变对象：

```java
public record User(
        String name,
        int age,
        boolean valid
) {}
```

编译器会自动生成：

* equals()
* hashCode()
* toString()

同时：

* 类是 final 的
* 字段是 final 的
* 没有 setter

对象一旦创建，其状态便无法改变。

看到这里，你可能会觉得：

> Record 不过是帮我少写了一些代码而已，这和函数式编程有什么关系呢？

事实上，Record 的意义从来不只是减少样板代码。

它所推崇的不可变数据模型，恰恰是函数式编程最重要的基础之一。

因为当对象不会变化时，我们对程序的推理会变得简单很多。

例如：

```java
User user = loadUser();
```

只要 user 是不可变的，那么：

```java
user.name()
```

现在返回什么。

一分钟后依然返回什么。

传给十个方法后依然返回什么。

它不会被某个地方偷偷修改。

也不会因为共享状态而产生各种诡异问题。

程序的行为开始变得可预测。

而可预测，正是函数式编程一直在追求的目标。

不过，仅仅做到不可变还不够。

因为对象虽然不变，函数本身依然可能偷偷做很多事情。

这就引出了函数式编程最重要的概念。

## 纯函数

来看下面这个方法：

```java
int add(int a, int b) {
    return a + b;
}
```

无论调用多少次：

```java
add(1, 2)
```

永远都会得到：

```java
3
```

这样的函数被称为纯函数（Pure Function）。

纯函数有两个特点：

第一，相同输入永远产生相同输出。

第二，没有副作用。

例如：

```java
int add(int a, int b) {
    return a + b;
}
```

这是纯函数。

而下面这个：

```java
int add(int a, int b) {
    System.out.println("执行计算");
    return a + b;
}
```

就已经不是纯函数了。

因为它产生了副作用。

打印日志、发送消息、修改数据库、更新缓存，本质上都属于副作用。

为什么函数式编程如此推崇纯函数？

因为纯函数最容易推理。

当你看到：

```java
add(1, 2)
```

时，你甚至不用运行程序，就知道结果一定是 3。

这种特性有一个专门的名字：

> 引用透明（Referential Transparency）。

一个表达式可以直接用其结果替换，而不影响程序行为。

这也是函数式编程能够进行各种优化和组合的基础。

## Java 与纯函数式编程

看到这里，你可能会产生一个想法：

> 那我是不是应该把所有代码都写成纯函数？

答案是：

不现实。

事实上，Java 本身就不是一门纯函数式语言。

像 Haskell 这样的语言，会从语言层面限制可变状态和副作用。

而 Java 并不会。

你依然可以：

```java
user.setName(...)

list.add(...)

repository.save(...)

redisTemplate.set(...)
```

因为业务系统本身就是建立在状态变化之上的。

订单需要创建。

库存需要扣减。

数据库需要更新。

消息需要发送。

这些事情本质上全都是副作用。

所以对于 Java 开发者来说，学习函数式思维并不是为了追求绝对纯粹。

而是为了学会：

* 优先使用不可变数据
* 尽量让核心逻辑保持纯函数
* 将副作用集中在边界层
* 用声明式思维代替大量流程控制

这就足够了。

## 总结

函数式思维并不是什么高深理论。

对于 Java 开发者来说，它本质上是在回答三个问题：

第一，我们应该更关注做什么，而不是怎么做。

第二，减少状态变化，让数据尽可能保持不可变。

第三，让函数尽可能只关注输入和输出，而不是偷偷修改外部世界。

Stream、Lambda、Record 这些特性看似彼此独立，但它们实际上都在推动同一个目标：

> 让代码变得更容易理解、更容易推理，也更容易维护。
